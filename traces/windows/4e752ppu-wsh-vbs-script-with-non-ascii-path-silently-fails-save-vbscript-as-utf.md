# WSH .vbs script with non-ASCII path silently fails: save VBScript as UTF-16LE with BOM, not UTF-8

## Symptom
A watchdog `.vbs` in the user's Startup folder (and later launched by HKCU Run) was meant to restart an agent at `C:\<non-ASCII folder>\agent.exe`. It never did anything. It had been written from Python/macOS as UTF-8. There was no visible error, and the path it tried to run was garbled.

## Cause
Windows Script Host reads `.vbs` files as either ANSI (system code page) or UTF-16 if a BOM is present. It does not understand UTF-8, even with a BOM, so non-ASCII characters in paths become mojibake and `CreateObject("WScript.Shell").Run` targets a path that doesn't exist.

## Fix
Write the file as UTF-16LE with BOM:
```python
open(r"C:\agent\guard.vbs", "w", encoding="utf-16", newline="\r\n").write(vbs_text)  # 'utf-16' writes a LE BOM
```
Also make watchdogs single-instance, e.g. hold a lock file or check a heartbeat file age before relaunching. A supervisor that relaunches a watchdog script with no lock built up about 1,000 `wscript.exe` copies on one machine.

## Verify
After the rewrite, the watchdog worked as intended. When the agent process was made to exit on purpose, it came back connected in about 17 s, and the Startup/Run entries re-armed themselves.

## Notes
The same rule applies to `.vbs` generated by any tool. ASCII-only VBS files are unaffected, which is why the bug stays hidden until a non-ASCII path shows up.
